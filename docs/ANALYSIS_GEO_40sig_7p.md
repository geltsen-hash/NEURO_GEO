# Анализ GEO_40sig_7p_dataset_gen.py

Проверено на Windows Server 2022, Python 3.12, empymod 2.6.0, 8 логических ядер.
Скрипт восстановлен из присланного файла, все цифры ниже — результат реального прогона, а не оценка «на глаз».

---

## 0. Присланный файл не запускается

`python -m py_compile` падает на строке 2: `invalid character '‘' (U+2018)`.
В файле:

* «умные» кавычки `‘ ’` вместо `'` (строки 2–5, 28–30, 108);
* потеряны символы `#` у комментариев-разделителей (строки 16–18, 26, 32–34, 94–96) — они стали синтаксическим мусором;
* потеряны отступы внутри `calculate_point`, `worker_generator` и блока `main`;
* `if name == 'main':` вместо `if __name__ == '__main__':` — даже после починки отступов блок бы просто не выполнился.

Похоже на порчу при копировании через мессенджер/редактор. Если локальная версия рабочая — этот пункт можно игнорировать, остальные замечания к нему не относятся.

## 1. Главное: зеркальная аугментация не даёт ни одного бита новой информации

`worker_generator` строит `X_mirror` (up↔dn, `alpha → 180-alpha`) и **считает для него полную физику** — это ровно половина всего времени счёта. Проверка на 60 случайных LHS-точках (`bench5.py`):

```
max |ZZ_mirror - ZZ_orig|         = 7.4e-12 град
max rel err |A_mirror - 1/A_orig| = 7.5e-13
max |phase_mirror + phase_orig|   = 2.8e-11 град
```

То есть отклик зеркальной модели — точное аналитическое преобразование исходного:

* 8 каналов `*_T{1..4}_Simm` (ZZ) — **не меняются вообще**;
* все `*_Amp` → `1/Amp`;
* все `*_Phase` → `-Phase`.

Следствия:

1. **Половина машинного времени тратится впустую.** Аугментацию нужно делать в памяти за микросекунды (в приложенной версии — `mirror_signals()`, совпадение с физикой 2.5e-14).
2. **Физический вывод, важный для постановки задачи:** компенсированные ZZ-каналы принципиально не различают «что сверху, а что снизу» — по ним `Rh_up` и `Rh_dn` неразличимы. Всю информацию об ориентации несут только ZX-каналы, причём в виде симметрии `S → 1/S`. Если сеть будет обучаться на подмножестве признаков без ZX, задача вырождена.
3. **Риск утечки train/val.** Зеркальная пара — детерминированная функция базовой точки. `np.random.shuffle` перемешивает строки только внутри чанка, пары остаются в одном файле, и при случайном train/test split зеркало базовой точки попадёт в валидацию → метрики будут оптимистично завышены. Делить нужно **по индексу базовой точки**, а не по строкам.

## 2. Время счёта (замерено)

| | мс на точку (1 ядро) | 5 млн точек, ядро-часов | на 8 ядрах |
|---|---|---|---|
| как сейчас (5 млн вызовов физики) | 20.3 | ≈ 28 | ≈ 3.5 ч |
| с аналитическим зеркалом (2.5 млн) | 20.3 | ≈ 14 | ≈ 1.8 ч |

64 вызова `empymod.dipole` на точку (16 пар TX–RX × 4 компоненты `ab`) — это минимум для текущей формулировки; дублирующихся пар нет. Попытка «схлопнуть» их в один вызов не проходит: `dipole` требует скалярную `z` у src и rec, а при наклоне прибора все z разные. Через `empymod.bipole` (он умеет массивы src/rec с индивидуальными z и dip) считается **в 10 раз медленнее** (332 мс против 31 мс на те же 20 пар) — не вариант. Реальные рычаги ускорения: аналитическое зеркало (×2) и число ядер.

## 3. Смещение выборки по анизотропии

```python
Rv_pl_base = np.clip(Rh_pl_base * aniso_ratio, RO_MIN, RO_MAX)
```

`Rh_pl` логравномерно до 1000, `ratio` до 5 → произведение выходит за `RO_MAX` у **15.5 %** точек (замер на LHS 400). У них `Rv` прилипает к 1000, а фактический коэффициент анизотропии становится каким угодно, но не запрошенным: средний эффективный `Rv/Rh` = 2.77 вместо 3.00, у 2 % точек он схлопывается почти в 1. То есть в области высоких `Rh_pl` датасет почти не содержит анизотропии, а на границе `Rv=1000` появляется искусственное скопление точек — LHS-равномерность там уже не работает.

В приложенной версии (`ANISO_ADAPTIVE=True`) координата LHS отображается на **допустимый** диапазон `[1, min(5, RO_MAX/Rh_pl)]` — прилипания нет. Альтернатива — ограничить `RO_MAX` для `Rh_pl` величиной `1000/5 = 200`.

## 4. Свойства выходных признаков (замер на 400 точках)

* NaN/Inf — нет.
* ZZ-фазы: −24…+1 град, узкий диапазон; линейные комбинации в `symm()` безопасны (до ±180 далеко).
* `|S|`: 0.063 … 22.1, распределение тяжёлохвостое, ~78 % (400 кГц) и ~55 % (2 МГц) значений лежат в [0.9, 1.1]. Для обучения такой признак лучше отдавать как `20*log10(|S|)` (дБ) — иначе сеть работает с почти константой, у которой информативные хвосты на порядки.
* ZX-фазы на 2 МГц упираются в границу: 0.09 % значений по модулю > 170 град. Это разрыв ±180 в целевой переменной — редко, но именно на этих точках лосс будет огромным. Штатное решение: хранить `sin/cos` фазы либо разворачивать её по разносу.
* 40 = 2 частоты × (4 ZZ + 4 разноса × 4). Заголовки согласованы с расчётом.

## 5. Что проверено и оказалось корректным

* Метки разносов соответствуют геометрии: `|T1−Rzx1|=0.96`, `|T5−Rzx1|=1.62`, `|T2−Rzx1|=2.28`, `|T4−Rzx1|=3.00`, и точно так же для B-стороны (`T2/T5/T1/T3` с `Rzx2`) — путаницы в подписях нет.
* Матрица `symm()`: строки нормированы (сумма 1), набор зеркально-симметричен (строка 1 ↔ строка 4, строка 2 ↔ строка 3).
* Знак разности фаз ZZ выбран последовательно (всегда «дальний минус ближний») для всех четырёх TX.
* `aniso = sqrt(Rv/Rh)` — правильное определение для empymod; `depth = [-D_up, D_dn]` монотонно возрастает, как требуется.
* Ограничение BLAS-потоков до 1 перед `import numpy` — сделано верно, это важно при `multiprocessing.Pool`.
* `S_b` с подстановкой `-Vzx` эквивалентна `conj((Vzz+Vzx)/(Vzz−Vzx))` — записано избыточно, но верно.

## 6. Инженерные замечания

| # | Проблема | Последствие / решение |
|---|---|---|
| 1 | Нет seed у `qmc.LatinHypercube(d=7)` | Датасет невоспроизводим; при перезапуске получится другая выборка. `seed=...` |
| 2 | Нет resume | Падение на 90 % (2250-й батч из 2500) — чанки на диске остаются, но новый запуск сгенерирует другую LHS и смешает две несогласованные выборки. Нужно пропускать уже посчитанные чанки и брать ту же LHS |
| 3 | `pq.ParquetDataset(TEMP_DIR).read()` | Весь датасет (5 млн × 47 float32 ≈ 0.94 ГБ + оверхед arrow/pandas, реально 2–3 ГБ) грузится в RAM одним куском. Потоковая запись через `pq.ParquetWriter` решает |
| 4 | Нет `try/except` в worker | Одно исключение empymod убивает весь `Pool` после часов счёта |
| 5 | `multiprocessing.cpu_count()` | Возвращает логические ядра; при HT/SMT это переподписка, для тяжёлого BLAS-счёта обычно быстрее число физических ядер |
| 6 | Компрессия parquet не задана | По умолчанию snappy; `zstd` даёт заметно меньший файл при тех же скоростях |
| 7 | Нет метаданных | Рядом с датасетом стоит сохранять seed, границы диапазонов, геометрию зондов и версию empymod — иначе через месяц не восстановить, чем сгенерировано |
| 8 | Модель — только средний слой анизотропный | Осознанное упрощение, но стоит зафиксировать в метаданных: сеть, обученная на нём, не увидит анизотропию вмещающих |

## 7. Приложенная исправленная версия

`GEO_40sig_7p_dataset_gen_fixed.py` — синтаксис восстановлен, ядро физики **бит-в-бит совпадает** с исходным (`max diff = 0.0`), плюс:

* аналитическое зеркало (×2 по скорости, расхождение с физикой 2.5e-14);
* `SEED`, resume по чанкам, потоковая склейка через `ParquetWriter(compression='zstd')`;
* `try/except` в worker (сбойная строка → NaN, пул живёт);
* `ANISO_ADAPTIVE` (по умолчанию включён; `False` возвращает старое поведение с `clip`).

Прогнан end-to-end на `N_SAMPLES=400`: 400 строк в parquet, ошибок нет.
Что **не** менялось намеренно: состав и порядок 40 признаков, формулы `symm`/`S_a`/`S_b`, геометрия зондов, тип `float32`. Рекомендации по log-амплитуде, sin/cos фазы и делению train/val по базовой точке в код не вносил — это меняет формат датасета, решать вам.
