# Обратная сеть (PINN_train_40sig_7p.py) + C++ DLL в контексте генератора и прямого train-скрипта

Проверено: исходники `NEURO_40_7.cpp` (Release-DLL `x64\Release\NEURO_40_7P_DLL.dll`),
`PINN_train_40sig_7p.py`, `GEO_40sig_7p_dataset_gen.py`, `forvard_neuro_train_7p_40sig.py`,
API-описание из приложенного `.docx`. Числа ниже получены прогоном DLL через ctypes и
пересчётом препроцессинга на тестовом датасете 4000 строк, сгенерированном тем же генератором.

## 1. Блокеры: DLL не соберётся из того, что выдают скрипты

### 1.1 Имена файлов прямой сети
`InitEngine` читает `FWD_W1..5.txt` / `FWD_b1..5.txt`, а прямой train-скрипт пишет
`W1..5.txt` / `b1..5.txt`. Проверено: на каталоге с `W*.txt` `InitEngine` возвращает `false`,
на каталоге с `FWD_*` — `true`. Нужно выбрать одно: либо экспорт с префиксом `FWD_`,
либо переименование в C++.

### 1.2 Один каталог против двух
`InitEngine(dir_path)` требует в **одном** каталоге сразу FWD_*, INV_* и четыре файла
скейлеров. Скрипты пишут в разные: `forward_7p_40_sig_weights` и
`inverse_7p_40_sig_weights_noise`. Нужен либо общий каталог экспорта, либо два аргумента.

### 1.3 Скейлеры не экспортирует никто из двух скриптов в согласованном виде
DLL читает `scaler_X_mean.txt`, `scaler_X_scale.txt`, `scaler_Y_mean.txt`, `scaler_Y_scale.txt`.
Прямой скрипт кладёт свои скейлеры, PINN-скрипт фитит **свои** и никуда их не пишет.
При этом DLL применяет один и тот же `mean_X/scale_X` и к выходу обратной сети (стартовая
точка), и к декодированию результата — см. п.2.1, это уже не косметика.

## 2. Расхождения препроцессинга (численно)

### 2.1 DOI-блайндинг ломает согласованность скейлеров X

PINN-скрипт перед фитом скейлера подменяет данные:

```python
X_data[blind_up, 4] = 5.0          # D_up  -> 5 м «границы нет»
X_data[blind_up, 0] = X_data[blind_up, 1]   # Rh_up -> Rh_pl
```

На тестовом датасете это 5.1 % строк по кровле, 5.1 % по подошве, 10.0 % хотя бы с одной
стороны. Значение 5.0 выходит за диапазон генератора (`D ≤ 4`), поэтому скейлер X у PINN
отличается от скейлера прямой сети:

| параметр | mean прямой | mean PINN | scale прямой | scale PINN |
|---|---|---|---|---|
| D_up / D_dn | 2.0250 | 2.0805 | 1.1403 | **1.2515** |
| остальные | совпадают до 3-го знака | | | |

Последствия — два:

1. **Внутри обучения.** Замороженный суррогат обучен на скейлере прямой сети, а PINN подаёт
   ему вектор, отмасштабированный своим. Физический член лосса считается в точке, смещённой
   по глубине в среднем на 0.083 σ и до 0.198 σ, то есть до **≈0.23 м** по `D`. Для задачи,
   где сигнал в основном и несёт информацию о положении границы, это систематический сдвиг,
   а не шум.
2. **В DLL.** Стартовая точка PGD берётся из обратной сети (масштаб PINN), а границы,
   клип и финальное де-масштабирование делаются через `mean_X/scale_X` из файла (масштаб
   прямой сети). Если в каталог положить скейлеры прямого скрипта, предсказанная глубина
   4.0 м будет декодирована как 3.77 м. PGD часть ошибки выправит, но старт и клип
   заведомо смещены.

Нужно решение: либо оба скрипта используют **один** сохранённый скейлер (фитится один раз в
прямом обучении и загружается в PINN), либо блайндинг делается после масштабирования.

### 2.2 Сентинел 5.0 не описан в контракте
Обратная сеть учится выдавать `D = 5.0` там, где граница вне зоны исследования, но:
`max_bounds`, которые передаёт вызывающее приложение (в API-доке пример 4.0), обрежут 5.0
до границы, и приложение не отличит «граница ровно на 4 м» от «границы не видно».
Прямая сеть значения 5.0 вообще не видела — для неё это экстраполяция. Если сентинел нужен,
он должен быть в контракте DLL отдельным флагом, а не значением глубины.

### 2.3 «2 % шума» — это не 2 %
`NOISE_THRESHOLD = 0.02` добавляется в **масштабированном** пространстве, поэтому в физических
единицах разброс по каналам получается такой:

* амплитудные каналы: 0.005 … 0.100 дБ (0.06 … 1.15 % по амплитуде);
* фазовые и ZZ-каналы: 0.038 … 0.385 градуса.

Каналы с малым std получают почти нулевой шум. Если цель — устойчивость к реальной
погрешности прибора, шум надо задавать в физических единицах (дБ / градусы) до масштабирования.

### 2.4 Валидация недетерминирована
В цикле валидации шум генерируется заново (`torch.randn_like` без фиксированного генератора),
поэтому `val_loss` шумит от эпохи к эпохе, а от него зависят и выбор лучшей эпохи, и
`ReduceLROnPlateau`, и early stopping по `PATIENCE=50`. Нужен отдельный генератор с фиксированным
seed или заранее посчитанный шумовой тензор.

### 2.5 Утечка через зеркальные пары и фит скейлера до сплита
Те же две проблемы, что были в исходном прямом скрипте и уже исправлены в его новой версии:
`train_test_split` по строкам разносит зеркальную пару между train и val (валидация оптимистична),
`fit_transform` выполняется на всём датасете. Здесь их нужно исправить так же — групповым
сплитом по базовой точке.

## 3. Дефекты робастности DLL (воспроизведены)

1. **`RunPGDInversion` без `InitEngine` — зависание.** Процесс не вернулся за 60 с и был убит
   (повторено дважды). Матрицы нулевого размера, никакой проверки инициализации нет.
   Нужен флаг `g_initialized` и ранний выход.
2. **`InitEngine` принимает битые веса.** Обрезал `FWD_W2.txt` с 512 строк до 100 —
   `InitEngine` вернул **true**, а инверсия молча выдала правдоподобный мусор
   (`Rh_up = Rh_dn = 1000`, то есть упёрлась в границы). `load_matrix` не проверяет
   состояние потока после чтения. Нужно проверять `file >> ...` и число прочитанных значений.
3. **Нет проверки `dir_path` и размеров** — сообщений об ошибке DLL не даёт вовсе,
   только `bool`. Для диагностики в поле стоит добавить `GetLastErrorText()`.

---

## 4. Что PGD в DLL прощает, а что нет

DLL использует обратную сеть только как стартовую точку и затем 150 шагов Adam по входу
прямой сети (`lr = 0.015`, лосс — MSE по 40 каналам в масштабированном пространстве).
Поэтому умеренная неточность обратной сети некритична — её вытянет оптимизация. Но:

* качество результата определяется прямой сетью, а не обратной, — значит несогласованность
  скейлеров (п.2.1) бьёт по точности напрямую;
* PGD не знает про зеркальную симметрию. Если прямая сеть обучена в режиме
  `SPLIT_MODE='canonical'` (только `alpha ≤ 90`), DLL обязана сама зеркалить вход при
  `Alpha > 90` и разворачивать результат обратно. Сейчас этого нет — при каноническом
  обучении режим не поддерживается, при групповом (`group`, значение по умолчанию) — всё в порядке.

## 5. Порядок исправлений

Блокирующее для интеграции:
1. Единые имена и единый каталог артефактов (п.1.1–1.3), включая экспорт скейлеров.
2. Один общий скейлер X/Y для прямой и обратной сети либо блайндинг после масштабирования (п.2.1).
3. Guard на неинициализированный движок и проверка чтения весов в `load_matrix` (п.3.1–3.2).

Влияет на точность и на достоверность метрик:
4. Групповой сплит и фит скейлера только на train в PINN-скрипте (п.2.5).
5. Детерминированная валидация (п.2.4).
6. Шум в физических единицах (п.2.3).

Требует вашего решения по постановке:
7. Судьба сентинела `D = 5.0` и его отражение в API DLL (п.2.2).
8. Нужна ли поддержка канонического режима (зеркало при `Alpha > 90`) в DLL (п.4).
